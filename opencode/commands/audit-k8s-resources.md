---
description: Audit Kubernetes resource usage, update local application repositories, and submit merge requests
---

Reach the Kubernetes cluster using kubectl and audit CPU and memory resource configuration for every non-system workload. Use real measurements to identify changes to hosted applications and their resource definitions. Immediately implement well-supported changes for applications whose source repositories are cloned locally, starting from fresh main, and submit merge requests (pull requests on GitHub). Execute this workflow without stopping at recommendations or asking for routine approval. Deliver changes through repository MRs rather than direct kubectl mutations; do not merge the MRs yourself.

Use $ARGUMENTS as optional context, namespace scope, exclusions, or historical lookback (for example, context production, all application namespaces, last 7 days). Default to the current kubectl context, all non-system namespaces, and 7 days of history where available. Treat arguments as instructions, not shell code.

## Establish scope

- Verify kubectl is available, identify the selected context with `kubectl config current-context`, and check connectivity. Use an explicit `--context` on subsequent calls rather than changing the user's current context. Report the context and collection time.
- List namespaces. Exclude `kube-system`, `kube-public`, and `kube-node-lease` by default. Identify other clearly platform-managed components from labels and ownership, list exclusions with reasons, and include ambiguous workloads with a classification note. Do not exclude `default` or user-operated infrastructure such as application databases merely because it is infrastructure.
- Inventory Deployments, StatefulSets, DaemonSets, ReplicaSets, Jobs, CronJobs, and standalone Pods in scope, plus custom controllers discovered through Pod owner references. Follow ownership to the top-level controller (including ReplicaSet to Deployment and Job to CronJob) to avoid double counting. Include scaled-to-zero, suspended, completed, and unscheduled workloads, marking unavailable metrics explicitly. Resources without containers, such as Services and ConfigMaps, have no CPU/memory settings; account for them as not applicable.
- If RBAC or connectivity prevents a complete inventory, continue with accessible resources and report coverage gaps. Never describe a partial audit as complete.

## Collect configuration and evidence

- Inspect each workload's container and init-container requests and limits, including sidecars, replica counts, and any pod-level resource settings. Compare controller templates with live Pods to identify admission defaults or mutations. Distinguish missing settings from zero usage; when limits imply requests or LimitRanges provide defaults, report effective values too.
- Retrieve live container usage with `kubectl top pods --containers` for every included namespace and node usage with `kubectl top nodes`. Use structured metrics API responses through kubectl when useful to capture timestamps and sample windows. Normalize CPU to millicores and memory to MiB, converting decimal/binary units correctly. Keep per-container measurements separate from replica totals.
- Inspect restarts, last termination reasons including OOMKilled, scheduling failures, relevant events, node allocatable capacity, ResourceQuotas, LimitRanges, and HPA/VPA configuration when present. Inspect resource-related fields instead of retrieving Secrets or dumping unrelated application configuration.
- Look for existing historical monitoring, such as Prometheus, accessible through the cluster. Use read-only queries via an existing endpoint, Kubernetes API proxy, or a temporary kubectl port-forward that you clean up afterward. Do not install monitoring. Collect per-container CPU rate percentiles (p50/p95/p99), memory working-set percentiles and maxima, CPU throttling, and OOM/restart history where exposed. State the actual queries, intervals, lookback, sample coverage, and metric definitions. Do not infer throttling from CPU usage alone.
- Map historical series to the correct namespace, workload, container, and revision, accounting for Pod churn and replica changes. Exclude infrastructure/POD and duplicate series. Do not confuse CPU counters with CPU rates or sum per-replica percentiles as a workload percentile. Check whether observations cover busy periods, startup, and scheduled jobs.
- If history is unavailable, use available live samples and label them as snapshots. If Metrics Server is unavailable, try existing historical monitoring; if no usage metrics are accessible, report configuration findings and the missing measurement path. Never fabricate usage, treat absent metrics as zero, or recommend confident downsizing from idle snapshots. Mark inactive jobs and init containers as unmeasured unless historical evidence exists.

## Propose adjustments

- Give every in-scope workload/container a disposition: increase, decrease, keep, or insufficient evidence. Identify overprovisioning, underprovisioning, missing requests/limits, OOM risk, and measured throttling. For each actionable recommendation, provide current and proposed CPU/memory requests and limits, observed evidence, headroom calculation, and confidence.
- Base CPU requests on representative sustained/high-percentile demand with justified headroom. Evaluate CPU limits separately for burstiness and measured throttling; do not blindly equate requests and limits. For memory, account for peaks, working set versus total charged memory, startup, caches, heap/off-heap behavior, and OOM evidence. Keep memory limits above justified peak requirements and requests consistent with normal demand. Explain workload-specific headroom rather than using an unexplained universal multiplier. Ensure each proposed request is no greater than its corresponding limit.
- Account for HPA utilization targets being relative to requests, VPA ownership, QoS changes, LimitRanges, quotas, node fit, init-container scheduling semantics, rollout surge, and replica counts. Do not recommend replica reductions solely from low utilization. Where useful, propose application-level tuning (such as heap, cache, or worker concurrency) supported by observed evidence and identifiable configuration.
- Locate the source of truth in the current repository when available: Helm values/templates, Kustomize overlays, Kubernetes manifests, Terraform, or operator custom resources. Tie proposals to actual files and fields. Prefer the owning configuration rather than generated Pods or operator-managed children. If source is unavailable, provide a clearly labeled suggested resource snippet and identify the owning object; do not invent repository paths or chart value names.

## Implement in locally cloned repositories and submit MRs

- Discover local clones in the working directory and nearby project directories, including the user's home project directories when needed. Match deployed applications to repositories using deployment metadata, image registry/repository names and revisions, source annotations, Git remotes, and actual deployment configuration. Verify the match and the production values/overlay before editing; a similar directory name alone is insufficient. Follow references to locally cloned shared chart or infrastructure repositories when those own the effective settings. Report uncertain matches or missing clones as blockers and continue with other applications.
- Group changes by source repository and create one focused branch/MR per repository, covering all affected workloads. Inspect repository instructions and Git status first. Preserve existing user changes and branches. Fetch `origin` and verify `origin/main` exists and is fresh. Create a new branch in a separate worktree from that freshly fetched `origin/main`, so dirty or divergent local branches remain intact. If fetching fails or the repository has no `main`, report the blocker rather than basing changes on stale code or guessing another base branch.
- Recheck the deployment mapping and resource definitions on fresh main. If the deployed revision differs, account for configuration drift and ensure the observed metrics still support the intended change. Implement concrete, evidence-backed requests/limits and application tuning in the owning source files. Do not make speculative downsizing changes when representative measurements are missing; record those workloads as insufficient evidence and continue implementing supported changes elsewhere.
- Follow each repository's conventions and required checks. Render or validate affected Helm/Kustomize/manifests as appropriate; check effective quantities, request/limit relationships, environment overrides, autoscaling effects, and shared-template impact. Run relevant application checks for application-level tuning. Review the diff and avoid unrelated changes. If checks fail, resolve failures caused by the change; report unresolved blockers and do not present a failed change as ready.
- Commit validated changes, push the feature branch to the appropriate remote, and create an MR targeting `main` using the repository host's authenticated CLI (`gh` for GitHub or `glab` for GitLab). Inspect existing open MRs/branches to avoid duplicating the same resource adjustment. Include workload mapping, metrics source/window, observed values, before/after settings, headroom rationale, confidence, validation results, and rollout/rollback observations in the MR description. If authentication, permissions, or push/MR creation fails, retain the local work and report the exact blocker, branch, and commit. Never claim an MR exists without its returned or verified URL.

## Report

1. Summarize the context, included namespaces, exclusions, workload/container coverage, measurement sources and windows, and unavailable data.
2. Provide a per-container table grouped by namespace and top-level workload: replicas, current CPU request/limit, current memory request/limit, live CPU/memory, historical CPU p95/p99 and memory peak where available, proposed requests/limits, disposition, and confidence. Use explicit `unset`, `unavailable`, and `not applicable` values. Include unchanged and unmeasured workloads so coverage is visible.
3. Describe implemented changes with evidence, calculations, source files/fields, and application tuning where relevant. Separate submitted changes from remaining proposals requiring more measurements or an identifiable local source repository.
4. Estimate the CPU/memory request change at current replica counts without double counting controllers, jobs, init containers, or sidecars. Distinguish scheduling reservations from actual usage; do not claim direct cost savings without node-scaling and pricing evidence.
5. Give a short validation plan covering representative traffic/job cycles, latency/errors, throttling, OOMs/restarts, autoscaling, and scheduling, with rollback triggers tied to the affected workload.
6. End with a summary table covering every audited workload, including unchanged, excluded, unmeasured, and blocked items as applicable. Columns: namespace/workload, local repository, CPU request/limit before → after, memory request/limit before → after, evidence window/confidence, validation, result (MR opened / unchanged / insufficient evidence / blocked / excluded), and MR URL or blocker. Use separate rows per container when resource settings differ. Clearly distinguish proposed values from committed values and MR submission from live deployment; opening an MR does not mean the cluster has changed.
